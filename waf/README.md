# WAF v3

Lua WAF for `lua-nginx-module`, refactored as modular components.

## Nginx include

```nginx
include conf/waf/waf.conf;
```

`waf.conf` contains:

```nginx
lua_shared_dict limit 20m;
lua_shared_dict waf_challenge 20m;
lua_package_path "conf/waf/?.lua;;";
init_by_lua_file "conf/waf/init.lua";
access_by_lua_file "conf/waf/access.lua";
```

## Module layout

- `config.lua`: all runtime config.
- `util.lua`: helpers.
- `request.lua`: request context builder (`ctx`) with lazy args/body readers.
- `rules.lua`: rule loader + cache.
- `logger.lua`: structured security logs.
- `checks.lua`: detection chain (`Checks.xxx(ctx)`).
- `challenge.lua`: challenge lock, verify endpoint, and pass-cookie issuance.
- `responder.lua`: response rendering.
- `engine.lua`: orchestration and single-pass context wiring.
- `init.lua`: warmup hook.
- `access.lua`: access phase entry.

## Rule files

Rule directory: `conf/waf/wafconf` (resolved from Nginx prefix).

- `whiteip`, `blackip`
- `whitereferer`
- `whiteurl`, `blackurl`
- `args`, `cookie`, `post`
- `useragent`, `tencent_useragent`

IP rule format (`whiteip` / `blackip`):

- exact IP: `203.0.113.10`
- CIDR: `203.0.113.0/24`
- regex: `^198\.51\.100\.\d+$`

## Notes

- This refactor intentionally removed legacy global/lib interfaces.
- Existing custom code must use the new modules (`engine/checks/rules/request/responder/logger`).
- Check order is configurable by `config.lua -> pipeline`.
- `white_referer` is available but disabled by default (`switch.white_referer = false`).
- `white_referer` matches full `Referer` header via regex and returns allow when matched.
- `Referer` can be absent or forged; do not treat it as strong authentication.
- Default behavior is fail-open (`runtime.fail_open = true`).
- To trust `X-Forwarded-For`, set `trust.forwarded_ip = true` only behind trusted reverse proxy.
- If output mode is `redirect`, update `output.redirect_url`.
- Block/CC/WeChat/Captcha pages are now generated by a unified template; edit copy in `config.lua -> page`.
- `whiteurl` bypass applies only when request has no query string.
- Challenge flow is server-side stateful: lock -> verify -> signed cookie -> release.
- Lock state keeps the original `continue` target in shared dict, so first redirect does not lose return path.
- Active lock always takes priority over old pass cookies (prevents stale-cookie bypass).
- When lock exists, only a same-batch valid pass-cookie can release it; stale cookies cannot.
- If lock creation fails (e.g. shared dict pressure), CC captcha mode auto-falls back to direct deny instead of fake challenge.

## Unified Config Entry

Edit only `config.lua` for operational tuning:

- `defaults`: global fallback constants (conf path, captcha path, status/json defaults, method list, limits).
- `route`: endpoint paths (`captcha_uri`, `captcha_verify_uri`, `deny_redirect_uri`).
- `paths`: rule/log directories.
- `parse`: header/args/body parse limits, `raw_headers`, and POST method set.
- `cc`: rate strategy and status code.
- `output`: block mode and output payload.
- `page`: brand/copy/theme for all rendered block pages.
- `pipeline`: ordered security check chain.
- `log`: `async/flush_interval/batch_lines/max_queue_lines/drop_policy` for high-hit logging performance.
- `challenge`: provider and verify flow config (`turnstile` / `native`, secret, cookie TTL, verify URI).

## Challenge Setup

When `cc.action = "captcha"`:

1. Set `challenge.secret` to a random 32+ byte value.
2. Keep `lua_shared_dict waf_challenge 20m;` in `waf.conf`.
3. Select provider:
   - `turnstile`: set `challenge.provider = "turnstile"` and configure `challenge.turnstile.site_key` + `challenge.turnstile.secret_key`.
   - `native`: set `challenge.provider = "native"` as internal fallback.
   - `turnstile` requires `lua-resty-http` and outbound HTTPS to Cloudflare verify endpoint.
4. If needed, customize routes:
   - `route.captcha_uri`
   - `route.captcha_verify_uri`

## Runtime Self-Test

Use bundled script to verify challenge flow in runtime:

```bash
chmod +x conf/waf/selftest_challenge.sh
BASE_URL="http://127.0.0.1" \
TARGET_URI="/" \
PROBE_URI="/robots.txt?__waf_probe=1" \
CC_BURST_MAX=80 \
conf/waf/selftest_challenge.sh
```

It validates:

- CC trigger enters challenge lock.
- Lock is enforced across URL changes (no "change URL then bypass").
- `continue` target persists from lock state.
- Native verify rejects wrong code and accepts correct code.
- Old pass-cookie cannot bypass newly created lock.

For `turnstile` provider, script runs prechecks and prints manual verification steps for final token solve.
